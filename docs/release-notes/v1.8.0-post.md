# uBixVault v1.8.0: a console you can run a vault from

uBixVault is a lightweight, open, Vault-API-compatible secrets manager: one small
Go binary, no plugin processes, and Vault's request shapes, so the `vault` CLI
and External Secrets Operator work unmodified. 1.8.0 is about **the console**.
Until now it was one long page of panels, enough to unseal and poke at a
secret. It is now an application you can do day-to-day work in, and it still
loads nothing from outside the vault.

## What changed

- **An application shell.** A sidebar groups the work into Dashboard, Secrets
  (Key/value, PKI) and Access (Users & roles, Tokens, Policies). Every page has
  breadcrumbs and its own address, so `/ui/#/kv/app/config` survives a reload
  and can be bookmarked or shared. While the vault is sealed, only Initialize
  and Unseal show; while you are signed out, only Sign in.
- **A dashboard.** Seal state and type, version, uptime, high availability and
  the active node, Raft peers and the leader, the signed-in token, and every
  secrets engine and auth method with what your token may do on it.
- **A key/value browser.** Folder-by-folder listing, values hidden until you
  reveal them, copy buttons, a JSON view, and the version history as a table
  with view, delete, undelete and destroy. Destroying a version asks you to
  type `destroy`. Revealed values are dropped when you leave the page.
- **Users & roles for every auth method.** List, create, edit and delete
  userpass users, AppRole, Kubernetes, JWT/OIDC and certificate roles, and LDAP
  groups. Passwords are never shown, and saving an edit without a password
  keeps the current one. AppRole shows the role ID and issues a secret ID that
  is shown once. Creating refuses a name that already exists.
- **Controls follow your permissions.** Create, Edit, Delete, New version,
  Undelete and Destroy appear only where `sys/capabilities-self` says your
  token may use them. A read-only user sees a read-only console. The server
  still checks every request; hiding a button is a convenience, not the
  control.
- **Sign in offers only what is set up.** The method picker lists token
  always, userpass once it has a user and LDAP once it is configured, and hides
  itself when only token remains. It reads a new unauthenticated endpoint,
  `GET /v1/sys/internal/ui/mounts`, which Vault's UI also uses.
- **Light and dark themes** that follow the system by default. The Theme
  button cycles System, Light and Dark.
- **Helm: unseal through your KMS or HSM.** `sealExternal` wires the
  external-command seal into the chart. The vault runs a command you supply to
  wrap and unwrap its master key, so the key that unlocks the vault can live in
  a cloud KMS or HSM outside the cluster instead of in a Kubernetes Secret. A
  helper init container brings the command into the distroless image. Off by
  default.

## What has not changed

The console is still plain HTML, CSS and JavaScript embedded in the binary,
with no build step and no third-party code. It runs under the same strict
Content Security Policy (`default-src 'none'`, scripts and connections to the
vault's own origin only). The token stays in the tab's session storage.

## What to know before you upgrade

- **One new unauthenticated endpoint.** `GET /v1/sys/internal/ui/mounts`
  answers without a token. It tells a caller whether userpass has any users and
  whether LDAP is configured, nothing more: no names, no counts, no machine
  auth methods or secrets engines. It answers `503` while sealed. If that is
  too much for your threat model, block the path at your ingress; the console
  then offers token sign-in only.
- uBixVault has had **no independent security audit**. That is still the open
  milestone. Raft storage remains **experimental**.

## Upgrading

Replace the binary or image (chart 0.1.25, appVersion 1.8.0). There is no
storage migration and no configuration change. To use the external seal, see
"Unsealing through your KMS or HSM" in the chart README.

```bash
helm upgrade ubixvault ./deploy/charts/ubixvault -n "$NS" -f values.yaml
```
